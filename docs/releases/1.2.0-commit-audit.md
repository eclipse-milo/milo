## Baseline, merge, and supersession reconciliation

- The release merge `d862b5e74` and version/README commits do not introduce the baseline
  runtime again. `OpcUaSubscription`, lazy type loading, and the core 1.05.07 generated
  model already exist in v1.1.6.
- `10a59c857` backports the transport stabilization/accepted-channel close barrier from
  `53a34760d`; `d7d5bdea9` ports integration-test changes from `caf4baf10`. Differences in
  branch context do not make these independent features. `c4d5251a7` and `cfe4dde4a` have
  identical stable patch IDs (Javadoc only).
- `git cherry` found no non-merge patch equivalent already reachable from the baseline.
  An inverse stable-patch-ID comparison found no complete-patch revert pairs. Diff and
  final-source review still account for partial reversals and replacements below.
- Seventeen merges have empty remerge diffs. Four have explicit resolutions: `abfc76dc3`
  chooses the shared test port allocator; `91a886c84` combines recovery hardening with ECC
  nonce/identity/header and generic reverse-transport monitoring; `c19e4e3ec` retains the
  integration endpoint/token-policy implementation while adapting incoming tests/examples;
  `9709f4eab` combines test additions. None introduces an extra feature beyond those linked.
- `f2024e659` merges the already-integrated `9709f4eab` result and has the same tree as that
  second parent. The tip merge likewise has the same tree as `17579b267`. They remain rows
  for reachability accounting, without double-counting their changes.
- Intermediate client certificate-manager/group-ID configuration is replaced by the final
  single-group/identity API. `DefaultApplicationGroup`'s temporary lifecycle/deprecation
  changes are superseded by its deletion. The guide shows actual v1.1.6 constructors and
  final `DefaultCertificateGroup`, not the intermediate APIs.
- The structure-matrix array restriction introduced during serialization optimization was
  corrected by `17bed13ce`; final generic codecs retain Object[] matrix support. Recovery
  implementations were also refined repeatedly: final behavior includes session/incarnation
  guards and the final reconnect recovery limits, not an early global 64-message assumption.
- Condition attach/adopt, custom instances, and application-driven limit states refine a
  runtime absent from v1.1.6. They are consolidated into the shipped capability and its
  limitations, rather than invented migrations from a released Condition runtime.

## Unresolved questions and review limits

There are no unresolved baseline/final API signature questions or unaccounted commits.
The following deployment questions remain outside the evidence established by this pass:

- Enhanced-policy interoperability and provider behavior with each target peer/runtime were
  not exercised. Source/tests establish supported paths, not external certification.
- Real GDS products, older optional-method behavior, and persistent enrollment recovery were
  not exercised. Generated GDS constants were not revalidated against an external NodeSet.
- Filesystem atomic moves, symlink watching, cross-process writers, trust persistence failures,
  and reconnect/event timing need deployment tests. The guide states the confirmed implementation
  limits and supplies checks instead of promising transactional durability or lossless recovery.
- Existing supporting docs are not all current in lifecycle phrasing. For example, alias
  package documentation describes manual startup after the server, while final server lifecycle
  participation also starts it safely before endpoint exposure. The guide follows final source.

For an incremental review, first pin the next tip and confirm this tip remains its ancestor.
Enumerate `b8377ea03e5ae3fe99de35487657db6bcd97bf1d..<new-tip>` without `--first-parent`.
Inspect new parent/merge-resolution diffs, append rows, and reconcile affected guide entries
against v1.1.6 and the new final tree. Update both reviewed-tip fields, coverage, date, samples,
and verification. If history was rewritten, compare reachability sets and redo supersession
accounting instead of assuming an append-only range.

As later 1.1.x releases appear, check which listed fixes they contain and clarify their
applicability in the guide. Keep the recorded comparison baseline unless deliberately
performing and documenting a new comparison.
