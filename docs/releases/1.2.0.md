# Milo 1.2.0 feature and migration guide

## Scope and reading guide

Use this guide to upgrade applications from Milo 1.1.x to 1.2.0.

The detailed comparisons and before-and-after samples use `v1.1.6`
(`fc8149465e176d3566289c552f782817e3ceda7d`) as the comparison baseline, with
`integration/1.2` pinned at `b8377ea03e5ae3fe99de35487657db6bcd97bf1d` on
2026-09-04. Last updated: 2026-09-04. The reviewed source identifies itself as
`1.2.0-SNAPSHOT`; this is a guide to that branch snapshot, not a claim about a later release.

Later 1.1.x releases may include some of the fixes described here. Check your starting
version when assessing behavior changes; not every listed fix will be new to your application.
The comparison does not inventory changes between 1.1.x releases.

The range is `fc8149465e176d3566289c552f782817e3ceda7d..b8377ea03e5ae3fe99de35487657db6bcd97bf1d`.
The baseline is an ancestor of the tip. All 140 commits reachable from the tip but not
from the baseline were reviewed, including 21 merges and their side histories. The
[commit audit](1.2.0-commit-audit.md) records coverage, resolutions, backports, and verification.

Client SDK users should start with identity configuration, subscription behavior, and
cache reset. Server SDK users should review certificate groups, endpoint selection,
event routing, and lifecycle ownership. Direct stack users also need the transport
and security API migrations. Recompile applications and extensions with one consistent
Milo version; 1.2.0 includes source and binary compatibility breaks.

`OpcUaSubscription`, lazy data-type loading, and OPC UA 1.05.07 core generated types
already exist in the baseline. Their presence alone is not a 1.2 feature. Feature
sections below describe capabilities; migration sections contain the upgrade actions.

## Major features

### Security policies and certificate identities

The stack adds 12 ECC policies, covering NIST P-256/P-384, Brainpool P256r1/P384r1,
and Curve25519/448 with AES-GCM or ChaCha20-Poly1305, plus `RSA_DH_AesGcm` and
`RSA_DH_ChaChaPoly`. SecureChannel handling and username/X.509 session authentication
support the enhanced policies. `SecurityPolicy.getProfile()` exposes their algorithm,
certificate, and channel requirements.

To enable a policy, provision a compatible identity in a `CertificateGroup`, configure
a matching server endpoint, and select that endpoint on the client. Runtime provider
support and certificate compatibility determine whether an endpoint can be advertised.
Only the AEAD-suffixed ECC policy URIs are supported; older suffix-less ECC URIs are
rejected. Existing RSA policies remain available.

`CertificateIdentity` joins a key pair, certificate chain, type, and owning group.
`CertificateIdentitySelector` selects compatible material for connection setup.
See the [stack security package][security-package] for supported profiles and providers,
and the [client](#client-identity), [server](#server-certificate-groups), and
[endpoint](#endpoint-selection-and-token-security) migrations before enabling them.
Supporting commits: [e164dca70][c-e164dca70], [b0d2ace86][c-b0d2ace86], [42e4dfc74][c-42e4dfc74].

### Reverse Connect

Clients can accept server-initiated OPC TCP connections. `OpcUaClient.createReverseConnect(...)`
uses either a shared `ReverseConnectManager` plus selector or a pre-claimed connection.
The application owns the manager and listener. `ReverseConnectAcceptor` supports discovery of candidates before creating
clients. On the server, `OpcUaServer.addReverseConnectTarget(...)` registers retrying outbound targets
and returns a handle for controlling them, backed by the TCP reverse connector.

Choose an ownership model, bind the client listener, register the expected server and
endpoint, configure the server target, and connect. Disconnect retained clients before closing registrations and managers. Manager shutdown
does not close claimed channels, and acceptor closure does not disconnect delivered clients.
The pre-claimed connection mode is one-shot: reconnect requires a new candidate and client.
Manager/selector mode rearms; discovery-first needs separate discovery and session connections. Treat ReverseHello as an unauthenticated admission/routing hint; authenticate the peer
through normal SecureChannel and Session checks after claim. Reverse Connect changes who opens TCP, while
OPC UA client/server service roles remain the same. It requires peer support and does
not apply to HTTPS or WebSocket transports.

Use the [Reverse Connect guide](../features/reverse-connect.md) for complete setup,
timeouts, endpoint selection, and shutdown examples. The
[architecture reference](../architecture/reverse-connect.md) describes the shared listener
and transport boundaries. See also [transport changes](#transport-extensions).
Supporting commit: [0b216aa42][c-0b216aa42].

### Node instantiation

`OpcUaServer.getNodeInstantiator()` builds typed object and variable instances from an
`InstantiationRequest`. It supports inherited declarations, optional members,
placeholder expansion, explicit NodeIds, staged callbacks, and method binding.
`describe()`, `plan()`, and `apply()` expose the stages; `instantiate()` performs the
usual combined operation. `InstantiationResult.root()` returns the typed root and
`deleteCreated()` removes the nodes and references created by that result.

Set the root identity, type, parent, and target `NodeManager` on the request before
instantiation. For events, use `getEventInstantiator()`. The replacement package is
explicitly experimental. Custom node managers have only the default best-effort batch
semantics unless they implement stronger storage primitives.

See [NodeFactory migration](#node-factory-migration) for persisted IDs and behavior
changes, and the [full instantiation guide](../features/node-instantiation-migration.md)
for optional members, placeholders, and callback mappings.
Supporting commits: [c3a54b35c][c-c3a54b35c], [186bcbadb][c-186bcbadb].

### Alarms and Conditions

The server SDK adds runtime `Condition`, `AcknowledgeableCondition`, and `AlarmCondition`
wrappers, discrete and limit alarms, trunk-state snapshots, acknowledgement/confirmation,
shelving, and ConditionRefresh handling. Concrete behavior factories such as
`AcknowledgeableCondition.create/attach/adopt` construct, attach to, or complete nodes.
Create/adopt use `ConditionBuilder`; attach uses `AttachOptions`. `OpcUaServer.getConditionManager()` owns runtime
registration and lookup. Limit alarms can evaluate values or accept application-driven
state; custom condition types can use the typed builder and lifecycle extension APIs.

Create or attach a condition, register it, connect its source to the event notifier
hierarchy, then drive changes through the runtime API. Registration and teardown are
part of correct use, including cancelling shelving work and retiring event IDs.
Persistence and restart recovery of application condition state remain application work.
See the [conditions package][conditions-package] and
[alarm example][alarm-example]; follow the [event and Condition lifecycle migration](#event-routing-and-condition-lifecycle).
Supporting commits: [beafad007][c-beafad007], [8f403eb04][c-8f403eb04],
[1892f41a0][c-1892f41a0], [23dc05cbc][c-23dc05cbc].

### Alias Names

The opt-in `org.eclipse.milo.opcua.sdk.server.aliases` package supplies Part 17 behavior
for the alias model already present in namespace 0. `AliasManager` and
`AliasManagerConfig` provide recursive wildcard search, category and alias mutation,
reference-type filtering, and `LastChange` version maintenance. Use the manager's
programmatic methods after startup to create the application vocabulary.

Applications own the alias NodeIds, categories, authorization, and `AliasVersionStore`.
The default store is in memory. Part 17 requires persisted `LastChange` across restarts;
supply durable version storage and restore alias/category definitions separately. Network configuration methods must be enabled and separately
authorized; mutation is denied by default. Direct address-space edits require a manager
`touch` to update versions, and inverse references must exist for deletion and ancestor
version propagation. Search is weakly consistent during concurrent edits and does not inherit Browse visibility
filtering; enforce access through `checkFind` and `includeResult`. FindAliasVerbose is disabled
by default. Defaults limit results to 1000, patterns to 512 UTF-16 characters, and mutations
to 1000 operations per call; there is no result paging. Programmatic mutations accept local
targets only. See also the [manual-handler migration](#alias-method-defaults).

See the [aliases package][aliases-package] and [AliasNamesExample][alias-example].
Use [server lifecycle participation](#server-lifecycle) to start the manager before
endpoints become visible. Supporting commits: [7ef6e44e8][c-7ef6e44e8], [b7fd9e366][c-b7fd9e366].

### GDS Pull client

Add `org.eclipse.milo:milo-sdk-client-gds` at the same version as the SDK.
`GdsClient.create(connectedClient)` resolves the GDS namespace and Directory and registers
the generated model. Its blocking and asynchronous methods cover application registration,
certificate requests, certificate groups, and trust-list metadata. Use
`resolveCertificateTypeId(...)` to match a desired type to the GDS group's advertised types.
It can return null to request a compatible abstract group default; custom namespace types
require exact matches, since the helper does not browse their subtype hierarchy.
`TrustListReader` reads the remote FileType, and `TrustListApplier` applies specified lists
to the chosen local group's `TrustListManager`.

The application owns connecting and disconnecting, enrollment scheduling, polling
`FinishRequest`, persisting application/request IDs, validating and installing issued
certificates, and deciding where pulled trust belongs. The client does not retry these
workflows automatically. Keep the authenticated client certificate stable between starting
a certificate request and calling `FinishRequest`. Generated server model classes are available, but they do not
supply a production GDS service. `milo-sdk-client-gds-testing` publishes `FakeGdsNamespace`
for tests and is included in the BOM alongside the client module.

Follow the [GDS client guide](../features/gds-client.md),
[GdsPullExample][gds-example], and [certificate persistence migration](#certificate-persistence-and-trust).
Supporting commits: [93c6e8f3e][c-93c6e8f3e], [340568ee7][c-340568ee7],
[58c23c5ab][c-58c23c5ab], [32a25c26a][c-32a25c26a].

### Server lifecycle participation

`OpcUaServer.addLifecycleParticipant(Lifecycle)` lets the server own application components.
Register them before startup. They start in registration order after the standard
namespaces and event facilities are ready, before passive and reverse endpoints become
visible. Shutdown and startup rollback stop successfully started participants in reverse
order. See [server lifecycle migration](#server-lifecycle) for failure handling and restart
constraints. Supporting commit: [b199d6cc2][c-b199d6cc2].

## Breaking changes and migration

### Client identity

If you configure a client application certificate, replace the separate `setKeyPair`,
`setCertificate`, and `setCertificateChain` calls on the `OpcUaClientConfig` builder with
`setCertificateIdentity(keyPair, chain)`. Pass the leaf certificate first, followed by
any issuer certificates. Keep your existing certificate validator.

Before, in v1.1.6 (given `endpoint`, `keyPair`, `chain`, and `validator`):

```java
var config = OpcUaClientConfig.builder()
    .setEndpoint(endpoint)
    .setKeyPair(keyPair)
    .setCertificate(chain[0])
    .setCertificateChain(chain)
    .setCertificateValidator(validator)
    .build();
```

After:

```java
var config = OpcUaClientConfig.builder()
    .setEndpoint(endpoint)
    .setCertificateIdentity(keyPair, chain)
    .setCertificateValidator(validator)
    .build();
```

Review the application URI your client sends. An explicit `setApplicationUri(...)` value
still takes precedence. Otherwise, Milo now derives the URI from the selected certificate's
SAN URI. Without a selected identity, it can use the configured group's single distinct
nonempty SAN URI; if neither yields a URI, it retains the placeholder fallback. An unchanged
builder call can therefore send a different application URI. Set the URI explicitly if
existing server registrations require it, and check that it matches the selected certificate
and any GDS registration.

If your application reads `config.getApplicationUri()`, update it for the return type change
from `String` to `Optional<String>`. The result now contains only an explicitly configured
URI. Use `client.resolveApplicationUri(identity)` when you need the effective URI for a
selected identity. This return type change also requires recompiling existing callers.

For managed trust or multiple certificate types, use `setCertificateGroup(group)`.
`DefaultCertificateGroup.forIdentity(...)` joins one supplied identity with application
trust, quarantine, and validation. A group's validator is the default unless overridden
with `setCertificateValidator`. The identity shortcut still uses an insecure validator
when none is supplied, as the baseline did. The last call to `setCertificateIdentity` or
`setCertificateGroup` replaces the other choice.

The old `OpcUaClientConfig.getKeyPair()`, `getCertificate()`, and `getCertificateChain()`
getters are also removed. Retain the identity material your application supplies, or use
`client.getCertificateIdentity(profile)` to obtain the identity selected for a security-policy
profile. When present, that identity exposes `keyPair()`, `certificate()`, and `certificateChain()`.

Identity selection requires policy-compatible certificate material. The shortcut rejects
empty chains, unsupported certificate types, or public-key/leaf mismatches at build time.
An incompatible or absent secured identity fails locally with `Bad_ConfigurationError`.
For example, a SHA-1-signed RSA certificate is inferred as RsaMin and is not offered for
Basic256Sha256. Replace incompatible material rather than relabeling it. A requested
certificate type is a selection preference, not an exclusive restriction.

Verify connection and session activation for each endpoint, explicit and derived URIs,
and certificate rotation. Updating a store does not replace an identity on an already-open
channel/session; disconnect and reconnect to adopt it. See [client config][client-config]
and [client implementation][client-source]. Supporting commits:
[b0d2ace86][c-b0d2ace86], [42e4dfc74][c-42e4dfc74], [12fd04d7c][c-12fd04d7c].

### Server certificate groups

`DefaultApplicationGroup` is deleted. Its replacement is `DefaultCertificateGroup` in
`org.eclipse.milo.opcua.stack.core.security`. Initialize the backing resources yourself.
The group is usable immediately and has no initialization, generation, or close lifecycle.
When Milo should provision missing certificates, call the separate
`CertificateFactory.createMissingCertificates(group)` before exposing endpoints.

Before (given initialized `trust` and `store`, plus `factory`, `quarantine`, and `validator`):

```java
var group = DefaultApplicationGroup.createAndInitialize(trust, store, factory, validator);
var manager = new DefaultCertificateManager(quarantine, group);
```

After:

```java
var group = new DefaultCertificateGroup(trust, store, quarantine, validator);
factory.createMissingCertificates(group);
var manager = new DefaultCertificateManager(group);
```

Omit certificate creation for externally provisioned identities. It preserves existing
material and propagates errors; a partial multi-type creation leaves successful earlier
creations installed. The four-argument group constructor supports RSA SHA-256 only;
use the overload with `List<NodeId>` for other supported certificate types.

The one-group manager constructor registers the group under
`NodeIds.ServerConfiguration_CertificateGroups_DefaultApplicationGroup`. For other groups,
use `new DefaultCertificateManager()` and `addCertificateGroup(groupId, group)`.
The old quarantine-based constructors are removed. Registration order defines precedence;
replacement retains its position. Removal/replacement does not close resources or wait
for active lookups. Use the same trust/quarantine resources in the group and its validator,
and close application-owned resources after their users stop.

Custom implementations also need these source and binary migrations:

| v1.1.6 API | 1.2 replacement or obligation |
| --- | --- |
| `CertificateGroup.getCertificateGroupId()` | `CertificateManager.getCertificateGroupId(group)` returns `Optional<NodeId>`; custom managers must implement it |
| `CertificateGroup.getCertificateFactory()` | Keep the factory in application code |
| Group with no quarantine/presence API | Implement `getCertificateQuarantine()` and `hasCertificate(NodeId) throws Exception`; distinguish absent from unreadable material |
| `CertificateGroup.Entry(groupId, typeId, chain)` and public fields | Record `Entry(typeId, chain)` with `certificateTypeId()` and `certificateChain()` accessors |
| `CertificateManager.getCertificateQuarantine()` | Use the validating group's quarantine; `getRejectedCertificates()` aggregates a deduplicated list across registered groups |

Fixed endpoint certificates remain supported. Alternatively, let a secure endpoint select
from the default registered group, or use `EndpointCertificateConfig` for an explicit
group/type selection. Verify advertised endpoints, group IDs, identity precedence, trust
and rejected lists, missing/unreadable stores, and rotation. See
[CertificateGroup][certificate-group], [DefaultCertificateGroup][default-group], and
[server configuration boundaries][server-package]. Supporting commits:
[0492cd6bf][c-0492cd6bf], [127ceebbf][c-127ceebbf], [42e4dfc74][c-42e4dfc74], [17579b267][c-17579b267].

### Certificate persistence and trust

For `KeyStoreCertificateStore`, PKCS#12 and the default `server-rsa-sha256` alias remain.
New settings support other standard certificate types and custom alias prefixes. Changing
a prefix does not rename stored entries; migrate aliases explicitly and verify the old
identity is found before enabling missing-certificate generation.

Writes now reload persisted contents, preserve completed external edits, write and fsync
a temporary file in the destination directory, then require an atomic move. The directory
must be writable and the filesystem must support atomic replacement; file writability
alone is insufficient. There is no non-atomic fallback. Failed writes restore the prior
in-memory entry. Concurrent writers still need external coordination: overlapping updates
from separate processes/store instances can overwrite each other.

`watchForChanges=true` now actually reloads changes and rearms the watcher; the default
remains false. Applications that previously observed stale values can now see external
updates. File-open/parse failures log errors and retain the prior store; entry-loading failures
can leave the newly loaded store active. Test symlink-based deployment
paths, repeated file replacement, malformed files, and restart. Close watched stores after use.

`TrustListManager` now extends `AutoCloseable` with a default no-op `close()`. The file
manager already required closure in 1.1.6; groups and validators borrow it. Add
`getSnapshot()`, `update(UnaryOperator<TrustListSnapshot>)`, and `replaceAll(...)` to
application integration where a four-list operation must be coherent. Built-in managers
publish immutable snapshots atomically; validators read one snapshot per validation.
Custom managers still compile with the default methods, but their sequential getters/setters
are not atomic. Override snapshot and update operations for equivalent guarantees, and
make update functions free of side effects because they may run more than once.

`LastUpdateTime` now advances with trust-list changes and directory reloads. Snapshot lists
are deduplicated and immutable. A GDS apply replaces each specified list, including clearing
specified empty lists, while preserving unspecified lists at commit time. Decode failures
leave the manager unchanged. Recheck anchors that a full replacement could remove.

File trust-list publication is not a durable multi-file transaction: write failures are
logged but the requested in-memory snapshot is still published. Confirm the disk state
and trust decisions after restart, concurrent updates, and persistence failures. See
[trust manager][trust-manager], [keystore implementation][keystore], and
[GDS guidance](../features/gds-client.md). Supporting commits:
[a0170a151][c-a0170a151], [2b6544926][c-2b6544926], [40a5e4f92][c-40a5e4f92],
[628046647][c-628046647], [dfe3591c7][c-dfe3591c7], [8e7352ca1][c-8e7352ca1], [9e8093914][c-9e8093914].

### Endpoint selection and token security

Servers previously selected endpoints independently with first-match searches. Channels
now bind one endpoint using transport profile, URL path, security policy, message mode,
and receiver certificate thumbprint. Host/port aliases sharing this key must have equivalent
authentication policies and certificates. Ambiguous configuration fails startup with
`Bad_ConfigurationError`. Combine intended token alternatives on one endpoint or distinguish
endpoints by path/policy/mode/certificate. Hostname aliases cannot select different authentication.

An unsecured channel without a configured None endpoint is discovery-only and cannot create
or activate sessions. Configure a real None endpoint if those sessions are intentional.
Secured OpenSecureChannel requires the receiver thumbprint. Session reactivation checks
the replacement channel's selected endpoint and original client identity.

Final certificate selection can omit endpoints whose group, compatible identity, or runtime
provider is unavailable. A None endpoint can obtain a default-group certificate for legacy
encrypted username/issued tokens. Failure of this implicit selection leaves it advertised
without that certificate; failure of an explicit certificate request omits it. Inspect
GetEndpoints output and logs rather than assuming every configured endpoint is advertised.

Client/server token handling is stricter. A certificate user token may no longer resolve
to policy None, which skipped proof-of-private-key verification in the baseline. Configure
an explicit non-None certificate-token policy. An explicitly specified non-None token policy must use the
secured channel's RSA/ECC public-key family, including signed X.509 tokens. Enhanced username secrets require a secured channel; this restriction
does not prohibit enhanced signed X.509 tokens on None channels. `UsernameProvider` selects
usable policies before invoking a custom chooser, so review chooser assumptions.

For direct policy users, do not dereference legacy algorithm getters across every
`SecurityPolicy.values()` entry. Enhanced policies return null for symmetric signature,
symmetric encryption, and key derivation; ECC also returns null for certificate signature.
Use `getProfile()`, the optional `find...Algorithm()` methods, or `isLegacy()` when the
operation is intentionally restricted to legacy policies. A legacy algorithm value of None
on an enhanced profile does not mean the channel is unsecured; use the profile to interpret
its protection. Update exhaustive enum switches.
The old two-argument `IdentityProvider` method remains supported; custom enhanced token
providers need `IdentityProviderContext` and the relevant CreateSession/channel bindings.
Use `SelfSignedCertificateBuilder.forEccApplicationCertificate(...)` for ECC extensions;
the plain constructor retains RSA-oriented defaults.

Verify startup and discovery for every endpoint alias; exercise anonymous, username, and
X.509 activation, invalid certificates, reconnect, and channel renewal with real peers.
Check clock synchronization for enhanced secrets (the default permitted signing-time skew
is five minutes). See [endpoint selection][endpoint-selection],
[security package][security-package], and [client identities](#client-identity).
Supporting commits: [e164dca70][c-e164dca70], [a6df70903][c-a6df70903],
[58e947506][c-58e947506], [b0d2ace86][c-b0d2ace86], [42e4dfc74][c-42e4dfc74].

### Node factory migration

The legacy factories remain available with their existing behavior. Adopting the new
instantiator is optional in this snapshot, but changes construction behavior. Replace
`nodes.factories.NodeFactory` usage with `nodes.instantiation.InstantiationRequest` and
`server.getNodeInstantiator()`. The replacement `BrowsePath` also lives in
`org.eclipse.milo.opcua.sdk.server.nodes.instantiation`; it is a different type from the
legacy factory path.

Before (given `OpcUaServer server`, `ManagedAddressSpace space`, an existing `parentId`,
`instanceId`, and `browseName`):

```java
UaObjectNode node = (UaObjectNode) space.getNodeFactory().createNode(instanceId, NodeIds.FolderType);
node.setBrowseName(browseName);
node.setDisplayName(LocalizedText.english("Folder"));
space.getNodeManager().addNode(node);
node.addReference(new Reference(instanceId, NodeIds.Organizes, parentId.expanded(), false));
```

After (import `org.eclipse.milo.opcua.sdk.server.nodes.instantiation.InstantiationRequest`):

```java
var request = InstantiationRequest.of(UaObjectNode.class, NodeIds.FolderType)
    .nodeId(instanceId)
    .browseName(browseName)
    .displayName(LocalizedText.english("Folder"))
    .parent(parentId, NodeIds.Organizes)
    .legacyPathStrings()
    .target(space.getNodeManager())
    .build();
UaObjectNode node = server.getNodeInstantiator().instantiate(request).root();
```

`legacyPathStrings()` preserves the previous derived identifier formula. Without it, the
new escaping of path separators and non-string root handling can change persisted child
NodeIds. Pin important IDs with `assignNodeId(...)` where needed.

Before switching, check these additional behaviors:

- Optional methods are omitted by default. Select them with `includeOptional(...)`; binding
  a method alone does not select it.
- Collisions fail by default rather than replace existing nodes. `REUSE_COMPATIBLE` retains
  the existing node's ownership; cleanup must not delete reused nodes.
- Declaration attributes now include modeled permissions/restrictions, AccessLevelEx,
  Historizing, and sampling interval. Test representative users and channels after migration.
- `onNode` hooks see a staged graph, and method binding follows commit. Describe structure in
  the request; do not mutate live/reused nodes in hooks expecting rollback to undo it.
- Custom `NodeManager` implementations need atomic batch/generation primitives to promise
  more than `BEST_EFFORT`. Inspect rollback diagnostics on failed apply.
- Invalidate `server.getTypeModelCache()` after direct declaration-attribute changes;
  in-place edits can bypass manager generation tracking.

Verify stable NodeIds, optional nodes/methods, access decisions, collision handling, and
cleanup on failure. The [full migration guide](../features/node-instantiation-migration.md)
covers callback mappings and placeholders. Supporting commits:
[c3a54b35c][c-c3a54b35c], [186bcbadb][c-186bcbadb].

### Event routing and Condition lifecycle

This affects existing event-producing servers even without adopting Conditions. The
baseline sent events to all registered listeners. On a non-Server monitored node, an
event is now delivered only when its SourceNode is that node or is connected below it
through `HasEventSource`/`HasNotifier` references, including subtypes. Monitoring the Server object
still receives all events; ordinary non-monitored listeners also retain global delivery.

Set `SourceNode` and maintain both directions of the notifier references. In a
`ManagedNamespace`, `registerEventNotifier(UaObjectNode)` sets SubscribeToEvents and connects
a top-level notifier to the Server. Link that notifier to its sources with HasEventSource.
Organizes or HasComponent alone is insufficient. The SDK SubscriptionManager now owns
event-item registration across namespaces; `onEventItemsCreated/Modified/Deleted` are
lifecycle notifications. Omitting registration in these callbacks no longer suppresses delivery.

Modeled instance methods must be called with an instance ObjectId. Calls on ObjectTypes
now fail (`Bad_MethodInvalid`, or `Bad_NodeIdInvalid` for Condition instance methods).
Type methods without a ModellingRule remain callable. Test source-specific monitoring,
permissions, disabled/sampling/reporting transitions, refresh, and method ObjectIds.

For the [new Conditions runtime](#alarms-and-conditions), register created, attached, or
adopted behavior before clients call methods or refresh. Unregistering or displacing it is
terminal for that runtime instance and releases timers/filters, separately from ownership
of address-space nodes. Restore snapshots before the first live event/refresh. An attached
timed-shelving flag without its deadline normalizes to Unshelved. Use the typed custom
create/attach/adopt APIs for vendor types and preserve their TypeDefinition/EventType.
Limit alarms require application-supplied values or `setLimitState`/`setLimitStates`;
`inputNode` does not install a sampler, and `setActive(true)` does not select a limit state.

For ordinary transient events, `server.newEvent(typeId)` returns an AutoCloseable
`TransientEvent`; fill event fields, call `fire()`, then close it. Do not dispose a persistent
Condition node after each emission. Supporting commits:

### Alias method defaults

Standard FindAlias method nodes existed in 1.1.6 with executable flags enabled and a
default unimplemented handler. They now start with Executable and UserExecutable false
until `AliasManager` enables them. Existing manual handlers must explicitly restore both
flags or adopt the manager. Neither `setInvocationHandler` nor the new
`bindInvocationHandler` enables those flags. Verify actual client calls, not just handler
installation. See [Alias Names](#alias-names). Supporting commit: [7ef6e44e8][c-7ef6e44e8].

### Subscription behavior

`OpcUaSubscription` and its async lifecycle API already exist in v1.1.6. Public lifecycle
signatures remain, but client applications, listeners, and subclasses need these checks:

| Previous behavior | 1.2 behavior and migration |
| --- | --- |
| The interval constructor kept counts derived from the default 1000 ms interval | It derives a roughly 10-second requested keep-alive and five-times lifetime count from the supplied interval. At 100 ms, requested counts change from 10/50 to 100/500. Set counts explicitly if old timing was intentional; inspect server revisions |
| Callback outer lists were mutable | Data/event item and value lists are unmodifiable. Copy before editing; event arrays are not deeply immutable |
| Keep-alive/status listeners ran outside the same ordered delivery work | They now participate in per-subscription delivery/backpressure. Keep callbacks short and offload long work. Listener exceptions are logged and isolated |
| Async lifecycle methods invoked overridable blocking methods | Blocking methods now await async methods composed from async services. Review subclasses overriding only one form. Async callers no longer pass through blocking overrides |
| Lifecycle calls could overlap; reset could wait for network work | Transitions serialize; reset supersedes in-flight operations without waiting. A late created subscription is best-effort deleted. Expect `Bad_InvalidState` from superseded/conflicting work |
| Failed modifications/deletions could lose pending work | Modifications and retryable item deletions remain pending; old-subscription deletion work is discarded after reset. Recreate/synchronize retained monitored items after recreating a subscription |
| Transfer-failure notification could control cleanup | New final `handleTransferFailure(StatusCode)` resets internally before async notification, bypassing `reset()` overrides. Use transfer listeners for recovery; same-signature subclass methods can now clash |

Use nonblocking async lifecycle calls from delivery/transport executors; do not wait on
network results there. To preserve the old 100 ms constructor counts explicitly:

```java
var subscription = new OpcUaSubscription(client, 100.0);
subscription.setLifetimeAndKeepAliveCalculated(false);
subscription.setMaxKeepAliveCount(uint(10));
subscription.setLifetimeCount(uint(50));
subscription.create();
```

Import `org.eclipse.milo.opcua.sdk.client.subscriptions.OpcUaSubscription` and static
`org.eclipse.milo.opcua.stack.core.types.builtin.unsigned.Unsigned.uint`. Set the counts
after construction; disabling calculation also prevents later interval setters from
recalculating them. These setters already exist in the baseline.

Publish processing now orders and deduplicates responses, repairs gaps asynchronously,
restores failed-request acknowledgements, and drains reconnect Republish before resuming
Publish. It can recover the Publish ceiling after transient `Bad_TooManyPublishRequests`.
Watchdogs pause during session/recovery gaps and resume with revised parameters. A paused
watchdog does not establish data freshness. Gap repair is bounded and can report data loss;
it is not durable event history or exactly-once delivery across application restarts.

Session keep-alive scheduling now uses
`min(configuredInterval, max(1000 ms, revisedSessionTimeout / 2))`. A server-revised short
timeout can increase Read traffic despite unchanged client configuration. Recovery preserves
subscriptions through failed session retries, while ordinary explicit close still deletes them.
If the TCP transport is explicitly disconnected during recovery, reactivation now stops in
Inactive instead of retrying indefinitely; explicitly connect again to resume.

Verify count revisions, listener exceptions and latency, simultaneous lifecycle calls,
reconnect with missing messages, transfer failure, reset during requests, monitored-item
resynchronization, and application data-loss handling. See [subscription lifecycle][subscription-source]
and [Publish recovery][publishing-source]. Supporting commits:
[2b52583aa][c-2b52583aa], [53800b0d7][c-53800b0d7], [a4966f29e][c-a4966f29e],
[632c37c50][c-632c37c50], [d5e515a61][c-d5e515a61], [192aa7e0d][c-192aa7e0d],

### Data-type cache reset

Lazy loading is an existing capability; eager remains the default. In 1.2,
`LazyClientDataTypeTree.getTreeNode(NodeId)` returns a tree snapshot with parent links
instead of a live tree node. Requery to see later resolutions, and do not mutate the
snapshot expecting to change the client cache. `getRoot()` was already a snapshot.

`resetDataTypeTree()`, explicit tree refresh, and `setDataTypeTreeFactory(...)` now invalidate
the derived dynamic data-type manager and encoding context together. Reacquire
`getDynamicDataTypeManager()` and `getDynamicEncodingContext()` after a refresh; old objects
held by the application remain old. Rebuild custom registrations through the configured
factory. Pair `DataTypeTreeFactory.lazy()` with `DataTypeManagerFactory.lazy()` when choosing
lazy operation; eager codec initialization over a lazy tree now warns because it only sees
resolved types.

Verify decoding after a server type change, a failed resolution, and a reconnect. Negative
resolution attempts can remain cached until reset/recreation. Browse and supertype traversal
now have bounds and cycle checks, with best-effort continuation-point release on limits;
they do not provide an unlimited fallback for malformed models. See [client type utilities][type-package].
Supporting commits: [bd99a77a4][c-bd99a77a4], [86714655b][c-86714655b],
[53f8e381a][c-53f8e381a], [451d709c9][c-451d709c9], [11e17d4ce][c-11e17d4ce], [f3c07cd56][c-f3c07cd56].

### Server lifecycle

For applications using the new [participant API](#server-lifecycle-participation), register
components before the first startup/shutdown. Ownership transfers to the server; do not
also call their startup/shutdown methods manually. Do not join the enclosing server's
lifecycle future from a participant callback. Removing a participant before startup returns
ownership to the application.

`OpcUaServer.startup()` is now single-flight and returns the same future on repeated calls.
A successful old future does not mean a stopped server restarted. Create a new server
instance to retry a failed or terminated server, and shut down a failed instance to release
its remaining namespace resources.

`AbstractLifecycle.startup()` now leaves the component STOPPED when `onStartup()` throws;
the baseline left it RUNNING. Subsequent `shutdown()` is therefore a no-op. Clean partially
acquired resources inside the failing startup path. Likewise, a participant whose startup
throws is not included among successfully started participants for rollback. Inject a startup
failure and verify partial cleanup, reverse stop order, failure propagation, and absence of
endpoint visibility before components are ready. See [server lifecycle boundaries][server-package].
Supporting commits: [7b2d3a1b3][c-7b2d3a1b3], [b199d6cc2][c-b199d6cc2].

### Transport extensions

Custom transport, service-request, and channel integrations must recompile and adapt these
source/binary changes. Normal SDK users still need the runtime shutdown/reconnect checks.

| v1.1.6 API | 1.2 API or action |
| --- | --- |
| `ClientApplicationContext.getKeyPair/getCertificate/getCertificateChain` | Implement `Optional<CertificateIdentity> getCertificateIdentity(SecurityPolicyProfile) throws UaException` |
| `ServiceRequestContext` without endpoint access | Implement `Optional<EndpointDescription> getEndpoint()`; empty means discovery-only |
| `ServiceRequest` / `UascServiceRequest` constructors | Supply the selected endpoint argument before the request |
| `UascResponseHandler.handleChannelError(UaException)` | `handleChannelError(Channel, UaException)`; forward the failed channel |
| `UascResponseHandler.handleChannelInactive()` | `handleChannelInactive(Channel)`; forward that channel through delegates |
| Protected `AbstractUascClientTransport` pending maps and `cancelRequestTimeout(long)` | Pending bookkeeping is private/reworked; use the base request/response path rather than mutating it |
| `ChunkEncoder.EncodedMessage(chunks, requestId)` | `EncodedMessage(chunks, requestId, signature)`; preserve binding footer bytes when produced, otherwise pass null |

`ServerApplicationContext.selectEndpoint(...)` has a default implementation; custom
selection must reject ambiguous non-equivalent matches. The public legacy encode/decode
overloads remain. Changed private nested encoder/decoder strategies are not extension APIs.

Request failure is now scoped to the channel that carried the request. Queued unwritten
requests with positive timeouts can survive a channel failure and use its replacement;
unwritten requests without timeouts fail. Timeouts begin before channel acquisition. Verify
that stale channel failure cannot fail replacement-channel work, and that terminal custom
transport disconnect eventually completes channel acquisition futures. Request failures
now complete on the configured executor, with inline fallback if it rejects execution;
verify callbacks that relied on completion-thread identity.

`OpcUaClient.disconnectAsync()` waits at most five seconds for CloseSession before
proceeding to transport disconnect. This does not bound an arbitrary custom transport's
shutdown. TCP server `unbind()` waits for accepted channels to close, including when the
calling thread is interrupted; do not block its Netty event loop waiting for that work.
See [client transport context][client-context] and [response handler][response-handler].
Supporting commits: [e164dca70][c-e164dca70], [0b216aa42][c-0b216aa42],
[53a34760d][c-53a34760d], [a6df70903][c-a6df70903], [5d3de374d][c-5d3de374d], [42e4dfc74][c-42e4dfc74].

## Other notable changes

### Serialization and interoperability

Binary encoding/decoding removes reflective array access and intermediate integer boxing,
while preserving generic structure matrices. This review did not measure a speedup.
OptionSet arrays/matrices in Variants now resolve their unsigned backing type correctly,
and null-array Variants consume ArrayDimensions so following fields stay aligned.
`OpcUaDataType.getBuiltinTypeId(unknownClass)` returns -1 instead of throwing a null-pointer
exception. Unsupported Variant values now fail with `Bad_EncodingError` rather than a raw
null-pointer exception or malformed output; update custom error handling as needed.
Valid existing wire encodings remain supported. Supporting commits:
[fd4a74015][c-fd4a74015], [17bed13ce][c-17bed13ce], [fbaf0c6f6][c-fbaf0c6f6],
[05c5bfceb][c-05c5bfceb], [43c664cff][c-43c664cff].

`UShort.valueOf` now caches 0..255 by default. Do not depend on distinct object identity
for equal values. `org.eclipse.milo.opcua.stack.core.types.builtin.unsigned.UShort.precacheSize`
controls the cache at class initialization (nonpositive disables, maximum 65536).
Java deserialization retains the serialVersionUID, resolves valid values through the cache,
and rejects invalid values with `InvalidObjectException`. This affects Java object identity
and malformed persistence input, not the OPC UA UInt16 wire format. Supporting commits:
[75f25c3f9][c-75f25c3f9], [b8e65c5ad][c-b8e65c5ad], [3480e85e1][c-3480e85e1].

### Smaller APIs, reliability, and build changes

- `CertificateUtil.decodeCrl/decodeCrls` handles CRL input; the GDS trust helpers validate
  encoded entries before applying them. [88afff1c4][c-88afff1c4]
- `UaMethodNode.bindInvocationHandler` also publishes declared nonempty argument metadata.
  `Reference.ORGANIZED_BY_PREDICATE` and public `LikeMatcher` support alias work; event LIKE
  matching keeps malformed-pattern handling at its existing boundary. [ef674c45d][c-ef674c45d], [7ef6e44e8][c-7ef6e44e8]
- Session setup futures now complete on synchronous failures, abandoned establishment
  sessions are best-effort closed, stale keep-alive responses are ignored, and transfer
  results stay paired with their requested subscription IDs. [d069c25ed][c-d069c25ed]
- Lazy codec resolution avoids treating another in-flight resolution as failure, and bad
  browse/read results no longer leave partially installed type ancestry. [15c0795c1][c-15c0795c1]
- Java 17 remains the baseline. Build plugin updates and integration-test stabilization do
  not impose a new application runtime dependency requirement. New GDS artifacts join the BOM.
  Some runnable client examples move into `ijt`, `prosys`, and `unifiedautomation` packages;
  update launcher class names using the [examples README][examples-readme]. [ea69dfd8b][c-ea69dfd8b], [0b216aa42][c-0b216aa42]

## Deprecations and limitations

| API or capability | Replacement or confirmed limitation |
| --- | --- |
| `NodeFactory`, its callback, `InstanceDeclarationHierarchy`, `EventFactory`, factory accessors | Use the [experimental instantiation API](#node-factory-migration); legacy behavior remains available |
| `RsaSha256CertificateFactory` | Prefer `AbstractCertificateFactory` for current certificate-generation helpers, including ECC |
| GDS binary dictionary adapter in `milo-dtd-core` | Deprecated for removal since 1.2.0; prefer GDS `DataTypeInitializer`. The broader legacy dictionary subsystem was already deprecated in the baseline |
| `DefaultApplicationGroup` | Removed, not merely deprecated; use [DefaultCertificateGroup](#server-certificate-groups) |
| Conditions | Only the trunk branch is implemented. Historical branches and durable application-state storage are not supplied. Stock silence/suppress/service-state/reset/group-membership method behavior is incomplete; custom handlers require application work |
| Custom limit alarms | Application supplies reduction/sampling. Custom fields cannot be atomically joined to the private standard limit transition/event boundary |
| Alias Names | Version persistence does not persist definitions; restore both under stable IDs. No result paging or remote-target mutation. Authorization must cover lookup results, not just Browse visibility |
| GDS Pull | No scheduler or durable enrollment controller. Issued-certificate helper checks key/URI, not full trust-path/expiry/usage. TrustListReader buffers the whole file without a total-size cap; chunking does not bound aggregate memory |
| Enhanced security | Provider capability and peer support must be verified. Brainpool needs Bouncy Castle; built-in resolution can use its own fallback provider. No external interoperability certification is claimed here |

The instantiation package is explicitly experimental for one minor release. That status
does not apply automatically to the other new packages. Some older GDS servers may omit
optional methods; handle their returned status codes. The reusable GDS fixture and generated
server model do not implement a production GDS/Push service. Rejected-list aggregation is a
Java API and does not by itself supply a GetRejectedList service handler.

## Upgrade checklist

- Check your starting 1.1.x version for fixes also described in this guide; the detailed
  comparison uses v1.1.6.
- Align all Milo artifacts and rebuild applications/extensions. Check removed config/group
  methods, constructor descriptors, and custom transport interfaces.
- Preserve intended certificate validation. Verify selected certificate type, key match,
  SAN/application URI, GDS registration, and reconnect after rotation.
- Register server groups under the intended IDs. Provision only genuinely missing material;
  verify existing PKCS#12 aliases survive upgrade and prefix changes.
- Check atomic-file support, directory permissions, repeated external store edits, trust-list
  update concurrency, restart persistence, and application-owned resource closure.
- Inspect advertised endpoints and token policies. Test equivalent hostname aliases,
  discovery-only None channels, all identity types, failed authentication, and renewal.
- If adopting Reverse Connect, configure endpoint selection and validation explicitly; test
  reconnect mode, discovery/production connection separation, and client/listener cleanup.
- If migrating factories, compare persisted NodeIds, optional methods, modeled permissions,
  collisions, cleanup, and type-model invalidation.
- Verify event SourceNode/notifier ancestry, item mode changes, and instance method ObjectIds.
  Register Conditions and test acknowledgement, refresh, shelving restoration, and unregister.
- If using aliases, enable the intended methods, enforce lookup/mutation authorization, restore
  definitions and durable versions, and check limits and manual-handler executable flags.
- For GDS, persist workflow IDs, handle pending/unsupported statuses, validate issued material,
  map remote groups to local groups, and verify specified-list replacement semantics.
- Check subscription requested/revised counts, callback immutability and latency, subclass
  dispatch, reset/transfer races, reconnect gaps, and application data-loss reconciliation.
- Reacquire dynamic type managers/contexts after reset and verify decoding after type changes.
- Test startup failure cleanup and terminal lifecycle behavior; do not treat repeated startup
  completion as a restart.
- Exercise custom transport channel replacement and disconnect. Check Variant failures and
  UShort value equality where applications depended on former behavior.

The [audit verification record](1.2.0-commit-audit.md#verification) identifies compiled samples,
source checks, and limits of this review. These checklist items include runtime and persistence
checks that compilation alone cannot establish.
