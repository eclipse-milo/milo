# Milo 1.2.0 feature and migration guide

This guide covers upgrading from Milo 1.1.7, the latest 1.1.x release, to 1.2.0. It has two
parts: the significant new features in 1.2.0, and the changes that may require code changes in
your application. Changes already released in 1.1.7 are not repeated here.

The guide describes `integration/1.2` at `43c6f21a2bd2cd8b259b25709f4fa921cd921c68`
(`1.2.0-SNAPSHOT`, 2026-09-30). The [commit audit](1.2.0-commit-audit.md) maps every commit
since v1.1.7 to this guide.

Recompile applications and extensions against one consistent Milo version. 1.2.0 includes
source and binary compatibility breaks.

## New features

### ECC and RSA-DH security policies

The stack adds 12 ECC policies, covering NIST P-256/P-384, Brainpool P256r1/P384r1, and
Curve25519/448 with AES-GCM or ChaCha20-Poly1305, plus `RSA_DH_AesGcm` and `RSA_DH_ChaChaPoly`.
SecureChannel handling and username/X.509 session authentication support all of them.
`SecurityPolicy.getProfile()` describes each policy's algorithm, certificate, and channel
requirements.

To enable a policy, provision a compatible identity in a `CertificateGroup`, configure a
matching server endpoint, and select that endpoint on the client. The server advertises an
endpoint only when the runtime provider and certificate support it. Only the AEAD-suffixed ECC
policy URIs are supported. Brainpool curves need Bouncy Castle.

`Aes256_Sha256_RsaPss` now works with the built-in JDK 17+ providers, without registering
`BouncyCastleProvider`.

See the [stack security package][security-package], and the
[client identity](#client-certificate-identity), [certificate group](#server-certificate-groups),
and [token policy](#endpoints-and-user-token-policies) changes before enabling them.

### Reverse Connect

Clients can accept server-initiated OPC TCP connections. `OpcUaClient.createReverseConnect(...)`
uses either a shared `ReverseConnectManager` plus selector or a pre-claimed connection, and
`ReverseConnectAcceptor` supports discovering candidates before creating clients. The application
owns the manager and listener. On the server, `OpcUaServer.addReverseConnectTarget(...)` registers
a retrying outbound target and returns a handle for controlling it.

Treat ReverseHello as an unauthenticated routing hint; the peer is authenticated through the
normal SecureChannel and Session checks after the connection is claimed. Reverse Connect requires
peer support and does not apply to HTTPS or WebSocket transports. The
[Reverse Connect guide](../features/reverse-connect.md) covers setup, endpoint selection,
timeouts, and shutdown.

### Node instantiation

`OpcUaServer.getNodeInstantiator()` builds typed object and variable instances from an
`InstantiationRequest`. It supports inherited declarations, optional members, placeholder
expansion, explicit NodeIds, staged callbacks, and Method binding. `instantiate()` runs the
whole operation, while `describe()`, `plan()`, and `apply()` expose its stages.
`InstantiationResult.deleteCreated()` removes what that result created. For events, use
`getEventInstantiator()`.

The package is explicitly experimental for one minor release. It replaces the legacy node
factories; see [legacy node factories](#legacy-node-factories) and the
[instantiation guide](../features/node-instantiation-migration.md).

### Alarms and Conditions

The server SDK adds a runtime for Conditions: `Condition`, `AcknowledgeableCondition`, and
`AlarmCondition` wrappers, discrete and limit alarms, acknowledgement and confirmation, shelving,
and ConditionRefresh. Factories such as `AcknowledgeableCondition.create/attach/adopt` build new
Condition nodes or take over existing ones, and `OpcUaServer.getConditionManager()` owns
registration and lookup. Limit alarms can evaluate values or accept application-driven state, and
custom Condition types can use the typed builder and lifecycle APIs.

Create or attach a Condition, register it, connect its source to the event notifier hierarchy,
and drive changes through the runtime API. Unregister it when done; that releases its timers and
handlers. Only the trunk branch is implemented, and persisting Condition state across restarts is
application work. See the [conditions package][conditions-package], the
[alarm example][alarm-example], and [event routing](#event-routing).

### Alias Names

The opt-in `org.eclipse.milo.opcua.sdk.server.aliases` package implements OPC UA Part 17 for the
alias model already in namespace 0. `AliasManager` provides recursive wildcard search, category
and alias mutation, reference-type filtering, and `LastChange` version maintenance.

The application owns alias NodeIds, categories, authorization, and the `AliasVersionStore`. The
default store is in memory; Part 17 requires `LastChange` to persist across restarts, so supply a
durable store and restore alias definitions yourself. Network mutation methods are disabled and
denied by default. Search does not inherit Browse visibility filtering; enforce access through
`checkFind` and `includeResult`. See the [aliases package][aliases-package] and
[AliasNamesExample][alias-example].

### GDS Pull client

Add `org.eclipse.milo:milo-sdk-client-gds` at the same version as the SDK.
`GdsClient.create(connectedClient)` resolves the GDS namespace and Directory and registers the
generated model. Its blocking and asynchronous methods cover application registration,
certificate requests, certificate groups, and trust lists. `resolveCertificateTypeId(...)`
matches a desired certificate type to a GDS group's advertised types. `TrustListReader` reads a
remote trust list, and `TrustListApplier` applies it to a local `TrustListManager`.

The application owns connecting, scheduling enrollment, polling `FinishRequest`, persisting
application and request IDs, and validating and installing issued certificates. The client does
not retry these workflows. `milo-sdk-client-gds-testing` publishes `FakeGdsNamespace` for tests;
it is not a production GDS. See the [GDS client guide](../features/gds-client.md) and
[GdsPullExample][gds-example].

### Server lifecycle participants

`OpcUaServer.addLifecycleParticipant(Lifecycle)` lets the server start and stop application
components. Register them before startup. They start in registration order after the standard
namespaces and event facilities are ready and before endpoints become visible, and they stop in
reverse order on shutdown or failed startup. Ownership transfers to the server, so don't also call
their startup or shutdown methods yourself.

### Sampling framework

`ManagedAddressSpace` now samples its data MonitoredItems with a `SamplingManager` of its own,
one `SamplingGroup` per sampling interval, and refreshes each item's read access result before
every sample. A device driver subclasses `SamplingGroup` to read its items with its own protocol
and keeps the scheduling, membership, initial samples, and access refresh. `SamplingManagerConfig`
sets interval bucketing, a minimum interval, the initial-sample debounce, and the read-access
policy, which asks the `AccessController` every cycle by default or answers from a server-wide
cache that `AccessControlManager.invalidateReadAccess` keeps current. See
[docs/features/sampling.md](../features/sampling.md) and the [`DeviceNamespace`][device-example]
example.

### Monitored-item read access

A data MonitoredItem whose Session may not read its Node is now created and reports
`Bad_NotReadable` or `Bad_UserAccessDenied` through Publish, and keeps reporting the current
answer as permissions change: the sampling framework re-checks before every sample, and the SDK
re-checks a Session's items when its identity or endpoint changes and when its Subscriptions are
transferred. A server that samples its own items refreshes them for the permission changes it
makes itself. The `AccessController` distinguishes a Node nobody can read (`Bad_NotReadable`)
from one this user cannot (`Bad_UserAccessDenied`) and does the same for writes with
`Bad_NotWritable`. `OpcUaServerConfigBuilder.setAccessControllerFactory` installs a
custom controller. See [docs/features/access-control.md](../features/access-control.md).

### Server certificate rotation

Clients and existing Sessions now survive a server certificate change. After a SecureChannel
handshake fails on a secured endpoint, the client can rediscover the endpoint and retry with the
new certificate. The refreshed endpoint must match the original in everything but the
certificate, and the new certificate must still pass the client's validator.

`OpcUaClient.create(String...)` installs an `EndpointResolver` for this automatically.
`create(OpcUaClientConfig)` does not; set one with `OpcUaClientConfigBuilder.setEndpointResolver`
if you build the config yourself. On the server, each `Session` keeps the certificate it
presented in CreateSession (`Session.getOriginalServerCertificate()`), so a Session created before
a rotation can still be reactivated.

### Method handler results and per-object binding

`AbstractMethodInvocationHandler.invokeResult(...)` can return a complete Call result, including
an Uncertain status with outputs or per-argument `Bad_InvalidArgument` results. Override
`getRequiredInputArgumentCount` to accept calls that omit trailing inputs.

Shared Method nodes can have a different handler per ObjectId.
`UaMethodNode.setInvocationHandler(NodeId, ...)` installs one directly, and `MethodBindings`
provides an application-owned registry that validates bindings and releases them on close.
Calls fall back to the Method's default handler.

### Client operation limit overrides

`OpcUaClientConfigBuilder.setOperationLimitOverrides(...)` takes a `Map<OperationLimit, UInteger>`
or a function, and adjusts the OperationLimits the client reads from the server. Use it for
servers that don't advertise limits, which otherwise leaves the client sending one operation per
request, or that advertise a higher limit than they enforce. An override applies when the server
doesn't advertise the limit or advertises 0. Otherwise the smaller of the two values wins, and an
override of 0 leaves the server's value unchanged. `OpcUaClient.getOperationLimits()` reports the
effective limits.

### Client certificate identity

The `OpcUaClientConfig` builder no longer has separate `setKeyPair`, `setCertificate`, and
`setCertificateChain` methods. Use `setCertificateIdentity(keyPair, chain)`, passing the leaf
certificate first, followed by any issuers. Keep your existing certificate validator.

Before (given `endpoint`, `keyPair`, `chain`, and `validator`):

```java
var config = OpcUaClientConfig.builder()
    .setEndpoint(endpoint)
    .setKeyPair(keyPair)
    .setCertificate(chain[0])
    .setCertificateChain(chain)
    .setCertificateValidator(validator)
    .build();
```

After:

```java
var config = OpcUaClientConfig.builder()
    .setEndpoint(endpoint)
    .setCertificateIdentity(keyPair, chain)
    .setCertificateValidator(validator)
    .build();
```

For managed trust or multiple certificate types, use `setCertificateGroup(group)` instead; the
last of the two calls wins. `DefaultCertificateGroup.forIdentity(...)` combines one identity with
application trust, quarantine, and validation.

`OpcUaClientConfig.getKeyPair()`, `getCertificate()`, and `getCertificateChain()` are removed.
Keep the material your application supplies, or call `client.getCertificateIdentity(profile)` for
the identity selected for a security policy.

`OpcUaClientConfig.getApplicationUri()` now returns `Optional<String>` holding only an explicitly
configured URI. When none is set, Milo derives the URI from the selected certificate's SAN URI,
so an unchanged configuration can send a different application URI than 1.1.7 did. Call
`setApplicationUri(...)` if existing server or GDS registrations depend on the old value, and use
`client.resolveApplicationUri(identity)` when you need the effective URI.

The certificate must suit the endpoint's policy. The builder rejects empty chains, unsupported
certificate types, and key/certificate mismatches, and a secured connection without a compatible
identity fails with `Bad_ConfigurationError`. For example, a SHA-1-signed RSA certificate is not
offered for Basic256Sha256; replace such certificates.

### Server certificate groups

`DefaultApplicationGroup` is removed. Use `DefaultCertificateGroup` in
`org.eclipse.milo.opcua.stack.core.security`. It has no initialization or close lifecycle, so
initialize the trust list and certificate store yourself. To have Milo create missing
certificates, call `CertificateFactory.createMissingCertificates(group)` before the server starts.

Before (given initialized `trust` and `store`, plus `factory`, `quarantine`, and `validator`):

```java
var group = DefaultApplicationGroup.createAndInitialize(trust, store, factory, validator);
var manager = new DefaultCertificateManager(quarantine, group);
```

After:

```java
var group = new DefaultCertificateGroup(trust, store, quarantine, validator);
factory.createMissingCertificates(group);
var manager = new DefaultCertificateManager(group);
```

The four-argument group constructor supports RSA SHA-256 only; use the overload with a
`List<NodeId>` of certificate types for others. The one-group manager constructor registers the
group as the DefaultApplicationGroup. For additional groups, use `new DefaultCertificateManager()`
and `addCertificateGroup(groupId, group)`. Close the trust list and store yourself after the
server stops.

Custom implementations need these changes:

| 1.1.7 API | 1.2.0 replacement |
| --- | --- |
| `CertificateGroup.getCertificateGroupId()` | `CertificateManager.getCertificateGroupId(group)`, returning `Optional<NodeId>` |
| `CertificateGroup.getCertificateFactory()` | Keep the factory in application code |
| No quarantine or presence methods on the group | Implement `getCertificateQuarantine()` and `hasCertificate(NodeId)` |
| `CertificateGroup.Entry(groupId, typeId, chain)` with public fields | Record `Entry(typeId, chain)` with `certificateTypeId()` and `certificateChain()` |
| `CertificateManager.getCertificateQuarantine()` | The validating group's quarantine; `getRejectedCertificates()` aggregates across groups |

Fixed endpoint certificates remain supported. A secure endpoint without one selects from the
default group, and `EndpointCertificateConfig` selects an explicit group and certificate type. See
[CertificateGroup][certificate-group] and [DefaultCertificateGroup][default-group].

### Custom trust list managers

`TrustListManager` adds `getSnapshot()`, `update(UnaryOperator<TrustListSnapshot>)`, and
`replaceAll(...)` so a four-list change can be applied atomically. The built-in managers implement
them. Custom managers still compile, because the defaults fall back to the sequential getters and
setters, but those defaults are not atomic. Override them if validators or GDS updates must see a
consistent trust list. Update functions can run more than once, so keep them free of side effects.

### Certificate revocation checking

Revocation checking now uses the JDK's public PKIX revocation checker. Remove
`--add-opens java.base/sun.security.provider.certpath=ALL-UNNAMED` from your JVM options; it is
no longer needed. `ValidationCheck.REVOCATION` is deprecated for removal and has no effect.

| Configuration | 1.1.7 without `--add-opens` | 1.2.0 |
| --- | --- | --- |
| No revocation flags (the default) | No revocation checking; a CRL listing the peer as revoked was ignored | A peer revoked by an applicable trust-list CRL is rejected. Missing CRLs are tolerated and logged |
| `REVOCATION` only | Revoked peers rejected; a CA without a usable CRL failed validation | Missing CRLs are tolerated. Add `REVOCATION_LISTS` to keep failing on them |
| `REVOCATION_LISTS` with `REVOCATION`, or `ALL_OPTIONAL_CHECKS` | Revoked peers rejected; missing CRLs failed validation | Unchanged: every CA-issued certificate needs a usable CRL |

Check the CRLs in your trust lists against peers you expect to accept. When the trust list has no
CRL for an issuer, the JDK fetches one from the certificate's distribution point, which can block
the channel's event loop for up to 30 seconds per unreachable host. On isolated networks, supply
the issuer's CRL through the trust list or lower `com.sun.security.crl.timeout` and
`com.sun.security.crl.readtimeout`.

`DefaultServerCertificateValidator` now reports unknown revocation status and path-building
failures as `Bad_SecurityChecksFailed`, as it already did for untrusted and revoked certificates.
If you match on specific status codes from the server validator, update that logic.

### Endpoints and user token policies

Server endpoint selection is now deterministic. Endpoints that share transport, URL path,
security policy, mode, and certificate must have equivalent user token policies, even when their
host names differ; otherwise startup fails with `Bad_ConfigurationError`. Combine token policies
on one endpoint, or distinguish the endpoints by path, policy, mode, or certificate.

An unsecured channel without a configured None endpoint can only be used for discovery. Configure
a None endpoint if you intend to allow unsecured sessions. The server may leave out an endpoint
whose certificate or provider is unavailable, so check GetEndpoints output rather than assuming
every configured endpoint is advertised.

User token rules are stricter. Username and issued-token secrets must use the same public-key
family (RSA or ECC) as a secured channel. Enhanced username secrets require a secured channel. An
enhanced certificate-token policy cannot be used over a legacy secured channel. `UsernameProvider`
and `X509IdentityProvider` filter out unusable policies before invoking a custom chooser, and
`X509IdentityProvider` fails with `Bad_IdentityTokenRejected` when no policy fits the user
certificate. Review custom chooser logic accordingly.

### Security algorithm and policy APIs

If you build JCA `Signature` or `Cipher` instances from `SecurityAlgorithm.getTransformation()`,
use `SignatureFactory` and `CipherFactory` in `org.eclipse.milo.opcua.stack.core.util` instead.
The `RsaSha256Pss` and `RsaOaepSha256` transformation strings changed, and those algorithms now
need the parameters from `SecurityAlgorithm.getAlgorithmParameterSpec()`, which the factories
apply.

Enhanced policies return null from the legacy symmetric signature, symmetric encryption, and key
derivation getters, and ECC policies also from the certificate signature getter. Code that iterates
`SecurityPolicy.values()` must not dereference them. Use `getProfile()`, the `find...Algorithm()`
methods, or `isLegacy()`. Update exhaustive switches over `SecurityPolicy`.

Custom identity providers for enhanced policies need the new `IdentityProviderContext`; the
two-argument method still works for legacy policies. Use
`SelfSignedCertificateBuilder.forEccApplicationCertificate(...)` to create ECC certificates.

### Event routing

This affects existing event-producing servers, even without Conditions. In 1.1.7 every event
reached every event monitored item. Now an item on a node other than the Server object receives an
event only when the event's SourceNode is that node or is below it through `HasEventSource` or
`HasNotifier` references. Items on the Server object still receive all events.

Set `SourceNode` on your events and add the notifier references in both directions. In a
`ManagedNamespace`, `registerEventNotifier(UaObjectNode)` marks a node as a notifier and connects
it to the Server; link it to its sources with `HasEventSource`. `Organizes` or `HasComponent`
alone is not enough.

The SDK now registers event items for all namespaces. `onEventItemsCreated/Modified/Deleted` are
notifications only, and skipping registration in them no longer suppresses delivery.

Modeled instance Methods must be called with an instance ObjectId. Calls on the ObjectType fail
with `Bad_MethodInvalid`, or `Bad_NodeIdInvalid` for Condition Methods.

### Alias Method nodes

The standard FindAlias Method nodes now start with Executable and UserExecutable set to false until
an `AliasManager` enables them. If you installed your own handler, either set both flags yourself
or switch to `AliasManager`. Installing a handler does not change the flags.

### Method handlers

The Call service now discards argument DiagnosticInfos from a handler unless the client requested
operation-level diagnostics. Their string table indexes must come from
`DiagnosticsContext.addString`, reachable through `InvocationContext.getCallDiagnostics()`.
Handlers that build their own string table indexes need to switch.

A result that breaks the Part 4 CallMethodResult rules is returned as `Bad_InternalError`. That
includes an `InvalidArgumentException` whose number of results differs from the number of inputs.

`AbstractMethodInvocationHandler.invoke` is no longer abstract. A subclass that overrides neither
`invoke` nor `invokeResult` still compiles and fails at runtime with `Bad_NotImplemented`.

### Legacy node factories

`NodeFactory`, `EventFactory`, and `InstanceDeclarationHierarchy` are deprecated but still work
as before. When you migrate to the [node instantiator](#node-instantiation), preserve persisted
NodeIds.

Before (given `OpcUaServer server`, `ManagedAddressSpace space`, an existing `parentId`,
`instanceId`, and `browseName`):

```java
UaObjectNode node = (UaObjectNode) space.getNodeFactory().createNode(instanceId, NodeIds.FolderType);
node.setBrowseName(browseName);
node.setDisplayName(LocalizedText.english("Folder"));
space.getNodeManager().addNode(node);
node.addReference(new Reference(instanceId, NodeIds.Organizes, parentId.expanded(), false));
```

After (import `org.eclipse.milo.opcua.sdk.server.nodes.instantiation.InstantiationRequest`):

```java
var request = InstantiationRequest.of(UaObjectNode.class, NodeIds.FolderType)
    .nodeId(instanceId)
    .browseName(browseName)
    .displayName(LocalizedText.english("Folder"))
    .parent(parentId, NodeIds.Organizes)
    .legacyPathStrings()
    .target(space.getNodeManager())
    .build();
UaObjectNode node = server.getNodeInstantiator().instantiate(request).root();
```

`legacyPathStrings()` keeps the old formula for derived child NodeIds; without it, child NodeIds
can change. Other differences to check when migrating:

- Optional Methods are omitted unless selected with `includeOptional(...)`.
- A NodeId collision fails instead of replacing the existing node.
- Instances copy modeled permissions, AccessLevelEx, Historizing, and sampling interval from
  their declarations.
- `onNode` callbacks see staged nodes, and Methods are bound after commit.
- Custom `NodeManager` implementations get only best-effort rollback unless they implement the
  batch primitives. Cleanup relies on `getReferences` returning the same `Reference` instances
  that were added; managers that rebuild references from storage must override
  `removeReferenceIfSame`.

The [instantiation guide](../features/node-instantiation-migration.md) maps the old callbacks.

### Server lifecycle

`AbstractLifecycle.startup()` now leaves the component STOPPED when `onStartup()` throws; 1.1.7
left it RUNNING. A later `shutdown()` does nothing, so release partially acquired resources inside
`onStartup()` before throwing. `LifecycleManager`, including `ManagedNamespaceWithLifecycle` and
`ManagedAddressSpaceWithLifecycle`, now shuts down the children that already started when a later
child fails.

`OpcUaServer.startup()` now returns the same future on every call. A stopped or failed server
cannot be restarted; create a new instance instead, and shut down a failed one to release its
resources.

### Custom identity validators

ActivateSession verification now uses the server certificate from the Session's CreateSession, so
reactivation keeps working after a certificate rotation. Custom `IdentityValidator`
implementations that read `session.getEndpoint().getServerCertificate()` or the channel's
certificate should use `session.getOriginalServerCertificate()` instead.

### Client API behavior

The blocking `writeXxx(...)` methods on generated typed nodes, including the GDS model, now throw
`UaException` when the Write returns any non-Good status, Uncertain included. In 1.1.7 they
returned normally. Catch the exception, or use the async forms, which still return the status.

Connection failures during the SecureChannel handshake now carry a `SecureChannelHandshakeException`
in the cause chain. Check the status code instead of the exception class, such as
`UaServiceFaultException`.

### Transport extensions

Custom transport, service-request, and channel code needs these changes:

| 1.1.7 API | 1.2.0 API |
| --- | --- |
| `ClientApplicationContext.getKeyPair/getCertificate/getCertificateChain` | Implement `Optional<CertificateIdentity> getCertificateIdentity(SecurityPolicyProfile) throws UaException`; return empty when there is no identity for the profile, and throw when selection fails |
| `ServiceRequestContext` without endpoint access | Implement `Optional<EndpointDescription> getEndpoint()`; empty means discovery-only |
| `ServiceRequest` and `UascServiceRequest` constructors | Pass the selected endpoint before the request |
| `UascResponseHandler.handleChannelError(UaException)` | `handleChannelError(Channel, UaException)` |
| `UascResponseHandler.handleChannelInactive()` | `handleChannelInactive(Channel)` |
| Protected pending-request maps and `cancelRequestTimeout(long)` in `AbstractUascClientTransport` | Private; use the base request and response path |
| `ChunkEncoder.EncodedMessage(chunks, requestId)` | `EncodedMessage(chunks, requestId, signature)`; pass null when there is no signature |
| `OpcTcpServerTransportConfigBuilder.setExecutor`, `OpcServerTransportConfig.getExecutor()`, `UascServerConfig.getExecutor()` | Removed, as 1.1.7 ignored them; use `OpcUaServerConfigBuilder.setExecutor` |
| `UascServiceRequestHandler(UascServerConfig, ServerApplicationContext)` | `UascServiceRequestHandler(ServerApplicationContext)` |

A custom `ServerApplicationContext.selectEndpoint(...)` must reject ambiguous matches. A client
transport that reconnects internally should override the new
`OpcClientTransport.sendRequestMessage(Callable, long)`, which builds channel-bound requests only
once the channel is ready. See [ClientApplicationContext][client-context] and
[UascResponseHandler][response-handler].

### Serialization

JSON now follows the OPC UA 1.05 mapping, so JSON written by 1.1.x may not decode. ExtensionObjects
put their fields inline beside `UaTypeId`, which is now the DataType id, and 1.2.0 cannot read the
1.1.x form. DataValues are flat rather than nesting a Variant, null ByteStrings and null array
elements are written as `null`, and a QualifiedName such as `"2:Name"` decodes to namespace 2.
Convert stored JSON, and re-test JSON exchanged with other applications.

The JSON and XML decoders are stricter. JSON members may appear in any order, but unknown or
duplicate members fail with `Bad_DecodingError`, and input is limited to MaxMessageSize characters
and MaxRecursionDepth nesting. XML array fields must be direct children of the field element, and
non-schema lexical forms such as integer overflow or date-only DateTimes are rejected.

Custom codecs and data-type managers need these changes:

- Replace `encodeUInt32("EncodingMask", ...)` and `encodeUInt32("SwitchField", ...)` with the new
  `UaEncoder.encodeEncodingMask` and `encodeSwitchField`, and use the matching `UaDecoder`
  methods, or VERBOSE JSON cannot round-trip your structures.
- Implement `DataTypeManager.getDataTypeId(NodeId)` in custom managers. The default returns null,
  and JSON encoding of Binary or XML ExtensionObjects then fails with `Bad_EncodingError`.
- Dynamic codecs decode subtype-enabled structure arrays, and ExtensionObject arrays in Variant
  fields, as `UaStructuredType[]`. Code that casts them to `DynamicStructType[]` or another
  concrete array type must change. Null ExtensionObjects decode as Java null.

`milo-encoding-xml` no longer depends on JAXB. If your application used `jaxb-runtime` or
`jakarta.xml.bind-api` through it, declare them yourself.

In binary, a Matrix with a zero or negative dimension is now written as an empty array, so peers
decode it as an empty array rather than a Matrix. A Matrix with elements but fewer than two
positive dimensions fails with `Bad_EncodingError`.

### Sampling and read access

CreateMonitoredItems no longer fails a data item whose Session may not read the Node with
`Bad_NotReadable` or `Bad_UserAccessDenied`. The item is created and the denial arrives as the
status of the item's DataValue in Publish, as Part 4 §5.13.2.1 requires, and is replaced by
values once access is restored. A client that treated the create-time failure as its signal must
look at the item's status instead. Event items and `Bad_SecurityModeInsufficient` still fail at
create.

The default `AccessController` now returns `Bad_NotWritable` for a Value write when the Node's
`AccessLevel` lacks CurrentWrite, before it consults `UserAccessLevel`. In 1.1.7 the controller
returned `Bad_UserAccessDenied` whenever `UserAccessLevel` lacked the bit and only the Node layer
reported `Bad_NotWritable`. The order now matches Read.

`SubscriptionModel` is deprecated. `ManagedAddressSpace` samples through a `SamplingManager` of
its own, so a namespace that constructed a `SubscriptionModel`, registered it with its lifecycle,
and forwarded the four data-item callbacks to it deletes all three. `ManagedAddressSpace` now
revises a requested sampling interval up to the next multiple of 50 ms and reports it to the
client, so a request of 0 becomes 50 ms where it was polled at 1 ms, and new items get a
debounced first sample. The revision also applies to a namespace that overrides the four
callbacks for its own sampler, whose items now carry the revised interval; to keep the intervals
it had, it also overrides `onCreateDataItem()` and `onModifyDataItem()`. A direct `AddressSpace`
that keeps forwarding to `SubscriptionModel` keeps its intervals. See the
[migration section](../features/sampling.md#migrating-from-subscriptionmodel).

`AccessController` and `DefaultAccessController` moved from `servicesets.impl` to the new `access`
package, which also holds the read access cache, scope, and listener. The server exposes them
through `getAccessControlManager()`; `getAccessController()` remains as a shortcut. Code that
referenced the interface by its old package updates the import.

`DataItem` gained `setReadAccessResult` and `getReadAccessResult` with no-op defaults; an
application `DataItem` implementation must implement them to enforce read access.
`OpcUaServerConfigImpl` has a new canonical constructor with an `accessControllerFactory`
argument, and the previous constructors remain as overloads.

| Deprecated API | Replacement |
| --- | --- |
| `NodeFactory`, its callback, `InstanceDeclarationHierarchy`, `EventFactory`, and their accessors | [Node instantiator](#legacy-node-factories) |
| `RsaSha256CertificateFactory` | `AbstractCertificateFactory` |
| `ValidationCheck.REVOCATION` (for removal) | None needed; use `REVOCATION_LISTS` for strict checking |
| GDS binary dictionary adapter in `milo-dtd-core` (for removal) | GDS `DataTypeInitializer` |
| `SubscriptionModel` | `ManagedAddressSpace`'s own `SamplingManager`; see [Sampling and read access](#sampling-and-read-access) |
